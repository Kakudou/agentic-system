# Parameter Discovery

## Purpose

Inventory inputs already exposed by authorized target navigation, client behavior, and published documentation. This is reconnaissance, not input testing: do not guess names, use wordlists, alter requests, replay state-changing flows, or automate collection.

## Scope And Request Contract

Before observation, load the [scope and request-contract baseline](references/scope-contract.md). Stop when authorization, target ownership, allowed methods, authentication state, rate limits, or evidence handling is unclear. Use the [scope/stop checklist](assets/scope-stop-checklist.md) to record that decision.

## Prerequisites

- Written program authorization and an in-scope target or endpoint.
- A request contract defining permitted observation and any authenticated test account.
- A browser, proxy history, client log, or documentation already available within that contract.
- A safe evidence location that excludes secrets and session tokens.

## Workflow

1. Record the target, authorization boundary, observation window, and approved client state in the [input/contract evidence worksheet](assets/input-contract-evidence-worksheet.md).
2. Observe normal, approved navigation and client behavior. Capture only requests and responses naturally generated by that behavior. See [input observation](references/input-observation.md).
3. Classify each observed input by location and declared or evidenced type using [input location and type classification](references/input-classification.md) and the [confidence matrix](assets/input-location-type-confidence-matrix.md).
4. Correlate client-observed fields with first-party documentation, schemas, or API descriptions without treating either source alone as proof of runtime acceptance. See [client and documentation correlation](references/client-documentation-correlation.md).
5. Apply the [confidence and false-positive controls](references/validation-handoff.md), redact sensitive values, and prepare the [recon handoff template](assets/recon-handoff-template.md).

## Evidence

For each candidate, preserve the endpoint and method, input name or JSON path, location, observed source, timestamp, redacted value shape, declared/evidenced type, confidence, and relevant request-contract limits. Preserve source locators or stable captures, not credentials, cookies, tokens, personal data, or full secret-bearing request bodies.

## Output

Produce an inventory, not a vulnerability claim. Separate:

- Confirmed observed inputs: present in an allowed request or first-party contract and attributable to the endpoint.
- Corroborated inputs: independently supported by both client observation and first-party documentation.
- Documentation-only or client-only candidates: unconfirmed and not ready for testing.
- Excluded observations: out of scope, ambiguous, sensitive, or stopped under the request contract.
