# Endpoint Observation

## Purpose

Capture route identity from authorized, already-occurring application behavior without expanding the target surface.

## Preconditions

- The host and account context are explicitly in scope.
- The observation arises from normal authorized navigation, a delivered artifact, or target-published documentation.

## Methodology

Record the exact scheme, host, normalized path, observed method, timestamp, triggering user action, and source. Browser developer tools may be used to inspect traffic generated by that action. Preserve only redacted metadata necessary to substantiate the observation. Do not alter paths, methods, parameters, headers, payloads, or authentication state to discover additional behavior.

## Interpretation

An endpoint is `observed` only when a request in the authorized context identifies its route and method. A documentation-only route is `documented`; an artifact string is a `hypothesis` until corroborated.

## False-Positive And Scope Controls

CDN, analytics, identity-provider, feature-flag, and third-party requests may be out of scope. Redirect destinations and embedded origins require independent scope confirmation. A successful static asset request does not establish an application API route.

## Evidence And Handoff

Attach a redacted network-record reference, user-action description, source URL or artifact hash, and scope decision. Put unresolved hosts or routes in the handoff as approval requests, not findings.
