# Infrastructure, CDN, and Edge Signals

## Purpose

Describe externally observable delivery and edge-provider indications without testing controls, bypasses, origin exposure, or security behavior.

## Preconditions

- The program explicitly allows observation of the target's normal public delivery path.
- Any public-provider record used is relevant to the exact hostname and collection period.

## Method

Use a permitted normal response or public provider documentation and records. Note only provider attribution that is directly disclosed or independently supported. Do not manipulate request headers, vary protocol behavior, seek alternate origins, conduct WAF tests, or compare error behavior unless explicitly authorized.

## Interpretation

- An edge indication supports an edge or delivery-path hypothesis for the observed request.
- It does not prove ownership, complete CDN coverage, WAF deployment, WAF policy, origin location, or a bypass condition.
- Treat cache behavior as request-specific and time-dependent.

## False-Positive Controls

- Resellers, shared infrastructure, and delegated DNS can obscure the actual provider relationship.
- A provider reference can be inherited from a third-party asset or historical configuration.
- Require corroboration before calling an attribution high confidence and retain contradictory observations.

## Scope and Rate Limits

Remain on the documented target and normal request path. Make no control-testing requests. Stop on block pages, challenges, rate limits, unexpected redirects, or uncertainty about whether a response is generated by a security control.

## Evidence

Preserve the hostname, timestamp, response or public-record locator, provider statement if any, and the distinction between edge observation and origin inference.
